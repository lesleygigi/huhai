# 019 国内静态托管 + 国内认证 / 数据库 的账号密码云存档方案

## 背景

当前项目已经可以作为纯前端静态网页游戏运行：

- 前端基于 `Vite + React + TypeScript`
- 构建后可以直接部署为静态站点
- 当前存档使用浏览器本地 `localStorage`

现有本地存档结构见：

- `src/engine/save.ts`
- `src/engine/settings.ts`
- `src/components/GameView.tsx`

当前实现满足：

1. 单机游玩
2. 单设备本浏览器读档
3. 无账号、无后端

但不满足：

1. 账号登录
2. 每个用户拥有自己的云端存档
3. 换手机、换浏览器后继续读取自己的进度
4. 面向中国大陆用户的稳定访问

在重新评估“无 VPN 的中国大陆用户普遍可用性”之后，原先的“海外静态托管 + 海外 BaaS”不应再作为主方案。  
本任务文档改为面向中国大陆用户优先的正式版本。

---

## 目标

在**不做原生 App、不上应用商店**的前提下，把本项目升级为：

1. 可通过网页链接在移动端游玩
2. 支持账号注册、登录、退出
3. 支持找回密码
4. 支持每个用户拥有 6 个独立云存档槽位
5. 支持同一用户跨设备读取和保存自己的进度
6. 尽量保证中国大陆用户在无 VPN 条件下也能稳定访问
7. 保留本地临时存档能力，避免网络波动时完全不可用

---

## 核心判断

### 一、第一版仍不建议自购云服务器

即使切换到国内方案，第一版依然**不建议**直接购买并维护：

- 云服务器 CVM / ECS / VPS
- 自建 Node 服务
- 自建数据库
- 自建鉴权系统
- 自建邮件服务

原因不变：

1. 你的核心目标是“上线能用的网页游戏账号系统”，不是“学习完整后端运维”
2. 自建会显著增加：
   - 运维门槛
   - 安全风险
   - 备份责任
   - 证书、域名、数据库、邮件、审计复杂度
3. 本项目真正需要的后端能力并不复杂：
   - 认证
   - 每用户私有存档
   - 找回密码
   - 少量管理数据

因此，本项目最合理的第一版仍然应为：

**静态前端 + 国内托管式 BaaS**

## 推荐方案

### 结论

本项目推荐采用：

1. **前端部署：腾讯 EdgeOne Pages**
2. **账号与云存档：腾讯云 CloudBase**
3. **正式域名：尽早确定，并按接入方案准备备案**
4. **备选静态托管：腾讯云 COS 静态网站 + CDN**

不再推荐作为中国大陆正式版主方案的方向：

- Cloudflare Pages + Supabase
- 海外静态托管 + 海外数据库认证
- 自购服务器 + 自建鉴权 / 自建数据库

原因很直接：

- Supabase 当前公开可选主区域有新加坡、东京、首尔等 APAC 区域，但没有中国大陆区域。对于中国大陆大众用户，这种跨境链路不适合作为正式版默认架构。 citeturn0search0
- Cloudflare 面向中国大陆优化访问本身是单独的 China Network 产品，且要求有效 ICP 备案，并且是独立订阅能力，不适合作为你当前项目的第一版基础架构。 citeturn0search1turn0search3

---

## 为什么改用腾讯云系

### 一、更符合中国大陆用户网络环境

你的目标用户里有大量“没有 VPN 环境”的中国大陆玩家。  
在这种前提下，前端托管、认证、数据库都放到国内云厂商体系里，会比“网页在海外、鉴权在海外、数据库在海外”的方案稳定得多。

### 二、产品组合更贴近当前项目

本项目只需要：

1. 静态网页托管
2. Web 端身份认证
3. Web 端数据库
4. 轻量后端能力

腾讯云现成可以拼出这一套：

- EdgeOne Pages：前端托管
- CloudBase：Web SDK + 身份认证 + 云数据库

EdgeOne Pages 官方定位就是前端开发和部署平台，适合静态站点和现代 Web 应用。CloudBase 官方则明确提供 Web SDK，可供 Web 页面直接接入。 citeturn3search0turn0search6

### 三、后续扩展仍然够用

未来如果你要补：

- 活动页
- 兑换码
- 玩家反馈
- 成就与统计
- 管理后台

CloudBase 也能继续承接，不会像“纯本地存档 + 静态站点”那样立刻碰顶。

## 总体架构

### 一、最终架构图

```text
玩家浏览器（手机 / PC）
    ↓
腾讯 EdgeOne Pages（静态前端）
    ↓
腾讯云 CloudBase Auth（账号、登录、会话）
    ↓
```

- 负责静态资源分发

#### 2. CloudBase 负责

- 账号注册
- 登录会话
- 找回密码 / 邮箱验证链路
- 每个用户的私有云存档
- 基于安全规则限制访问权限

#### 3. 前端负责

- 登录 / 注册 / 找回密码 UI
- 登录状态管理
- 保存到云端
- 从云端加载存档
- 网络失败时回退到本地缓存

## 认证方案

### 一、第一版推荐：邮箱作为账号标识

虽然你提的是“用户名和密码”，但第一版在国内方案里，**最稳妥的实现方式不是先做独立用户名体系**，而是：

- 底层登录标识：邮箱
- UI 可显示为“账号”
- 密码：正常密码登录
- 昵称 / 用户名：后续单独加展示字段

原因：

1. CloudBase 官方支持邮箱登录
2. CloudBase 也支持用户名密码登录，但它要求用户先通过其他方式完成注册，再绑定用户名
3. 对当前项目而言，先把“邮箱 + 密码 + 云存档”跑通，比一开始做真正的自定义用户名体系更稳 citeturn1search4turn0search1

### 二、为什么不建议第一版就强做“自定义用户名登录”

CloudBase 的用户名密码登录官方流程本身是：

1. 先通过其他方式注册
2. 注册时绑定用户名
3. 后续再用用户名密码登录

这意味着它不是“最简单直接的初版方案”。 citeturn0search1

因此第一版建议改成：

- **账号 = 邮箱**
- **密码 = 用户自己设置的密码**
- **昵称 = 可选展示名**

如果你非常在意“用户名”这个显示层概念，可以：

- 界面文案写“账号”
- 实际底层用邮箱

这样体验上仍然成立。

### 三、找回密码

必须做。

只要做了密码登录，就必须提供：

- 忘记密码入口
- 邮件验证码 / 邮件重置流程

## CloudBase 认证策略

### 一、推荐落地方式

第一版建议这样设计：

1. 新用户通过邮箱验证码完成注册
2. 注册时设置密码
3. 老用户支持邮箱 + 密码登录
4. 保留邮箱验证码作为找回密码和验证渠道

CloudBase 官方文档中，邮箱登录 v2 就是验证码式流程；注册时可设置密码。已有用户也可以通过邮箱流程登录。 citeturn1search4

### 二、未来可选扩展

后续如果你想强化“用户名感”，再加：

1. 昵称字段
2. 唯一展示名
3. 真正的用户名绑定

但这些不应阻塞第一版上线。

## 存档策略

### 一、继续采用“双层存档”

不要把现有本地存档完全删掉。  
应改为：

1. **本地存档层**
   - 快速读写
   - 页面刷新恢复
   - 断网兜底

2. **云存档层**
   - 用户级持久存档
   - 跨设备同步
   - 正式账号系统下的主存档来源

### 二、第一版同步规则

采用最稳妥的规则：

**最后写入覆盖（last write wins）**

即：

- 每条存档以 `updated_at` / `saved_at` 为准
- 保存时直接覆盖该用户该槽位旧记录
- 登录后拉取云端 6 个槽位
- 云端为空则显示空槽

第一版不要做复杂冲突合并。

## 数据库设计

### 一、主集合 / 主表：`save_slots`

无论最终落在 CloudBase 数据库的文档集合还是表式抽象，逻辑结构都建议保持一致：

```ts
type CloudSaveSlot = {
  _id?: string;
  userId: string;
  slotId: number; // 1..6
  version: number;
  chapterName: string;
  sceneName: string;
  inkStateJson: string;
  history: unknown[];
  dialogueHistory: unknown[];
  savedAt: string;
  createdAt: string;
  updatedAt: string;
};
```

### 二、字段解释

- `userId`：归属哪个登录用户
- `slotId`：第几个槽位，固定 1 到 6
- `version`：存档结构版本号，供未来迁移使用
- `chapterName` / `sceneName`：展示用
- `inkStateJson`：核心 Ink 状态
- `history`：选择历史
- `dialogueHistory`：对话历史
- `savedAt`：玩家保存时间
- `updatedAt`：云端记录更新时间

### 三、唯一性约束

业务上必须保证：

- `userId + slotId` 唯一

即每个用户每个槽位只有一条当前生效记录。

## 权限设计

### 一、核心目标

只允许：

- 登录用户读取自己的存档
- 登录用户写入自己的存档
- 登录用户删除自己的存档

### 二、CloudBase 安全规则原则

CloudBase 官方支持通过安全规则控制客户端对数据库和存储的访问。匿名用户也可以单独限制。 citeturn1search1turn0search10

本项目建议规则思路为：

1. 未登录用户：
   - 不允许访问云存档集合
2. 已登录用户：
   - 仅允许 `userId == 当前登录用户 ID`
3. 管理端 / 控制台：
   - 保留后台全量权限

### 三、执行原则

第一版不要把权限判断散落在前端里。  
前端只负责提交带用户身份的请求，真正的数据隔离必须放在 CloudBase 安全规则层。

## 云存档接口设计

### 一、建议封装的函数

```ts
signUpByEmail(email, password, verificationCode)
signInWithEmailPassword(email, password)
signOut()
requestEmailVerification(email)
requestPasswordReset(email)
getCurrentUser()

listCloudSlots()

saveCloudSlot(slotId, saveData)
deleteCloudSlot(slotId)
```

### 二、保存策略

保存某个槽位时：

1. 先写本地
2. 若已登录，再写云端
3. 云端成功后更新 UI 状态
4. 云端失败则保留本地成功结果，并提示“云同步失败”

### 三、读档策略

#### 已登录

1. 页面启动后先恢复本地运行状态
2. 用户会话恢复完成后拉取云端槽位
3. 槽位列表以云端为准
4. 若云端读取失败，则回退到本地槽位并提示

#### 未登录

1. 直接使用本地槽位

因为项目现在已经有本地槽位，登录功能上线后，需要定义“本地转云端”的处理方式。

### 推荐规则

## 域名与备案

### 一、正式域名建议

应尽早确定正式域名，例如：

- `game.example.com`

原因：

1. 登录回调与邮件链接要稳定
2. 本地缓存与域名绑定，频繁换域名会影响存档体验
3. 后续备案、CDN、站点配置都要围绕正式域名展开

### 二、备案判断

如果最终站点托管在中国大陆资源上并面向中国大陆公开提供服务，通常需要准备 ICP 备案。公开文档中，阿里云也明确说明：如果网站托管在中国大陆实例上，则需要 ICP filing。 citeturn0search4

因此，本项目的执行口径应为：

1. **开发联调阶段**：先用测试域名 / 测试环境
2. **正式上线前**：确认正式域名
3. **正式面向大陆公开发布前**：核对是否需要备案，并提前准备

这里不要等上线当天再处理备案问题。

7. 用户在手机和电脑上登录同一账号后可读取同一云存档
8. 网络失败时，本地存档仍可作为兜底
9. 正式网页链接在移动端浏览器可正常游玩
10. 中国大陆普通用户在无 VPN 条件下可正常访问

## 备选方案说明

如果未来要做：

- 海外用户版
- 国际版镜像站
- 海外社区测试服

再考虑把“Cloudflare Pages + Supabase”恢复为国际版备选。  
但对于当前项目的正式生产版口径，`019` 已明确改为：

**国内静态托管 + 国内认证 / 数据库。**

---

## 最终建议

对你当前的项目阶段和目标用户结构而言，最合理的路线不是“先学买服务器”，也不是“先用海外服务碰碰运气”，而是：

**把前端、认证、数据库都放到国内可稳定访问的托管服务上，先把账号和云存档做成。**

这样最贴近真正能上线、能让中国大陆用户直接打开就玩的版本。
