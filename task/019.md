# 019 CloudBase 静态托管 + CloudBase 认证 / 数据库 的账号密码云存档方案

## 背景

当前项目已经可以作为纯前端静态网页游戏运行：

- 前端基于 `Vite + React + TypeScript`
- 构建后可以直接部署为静态站点
- 当前存档使用浏览器本地 `localStorage`

现有本地存档结构见：

- `src/engine/save.ts`
- `src/engine/settings.ts`
- `src/components/GameView.tsx`

当前实现满足：

1. 单机游玩
2. 单设备本浏览器读档
3. 无账号、无后端

但不满足：

1. 账号登录
2. 每个用户拥有自己的云端存档
3. 换手机、换浏览器后继续读取自己的进度
4. 面向中国大陆用户的稳定访问

此前曾尝试采用 `EdgeOne Pages` 作为静态托管前端，但实际联调中已确认：

1. 默认预览链接存在时效限制
2. 若想稳定公开访问，最终仍会落回自定义域名与备案问题

而你当前明确希望：

- 先不买域名
- 先不做备案
- 先把网页游戏账号与云存档跑通

因此，本任务文档改为：

**优先使用 CloudBase 自带的静态网站托管默认域名，完成第一版可用版本。**

---

## 目标

在**不做原生 App、不上应用商店、不立即购买域名**的前提下，把本项目升级为：

1. 可通过网页链接在移动端游玩
2. 支持账号注册、登录、退出
3. 支持找回密码
4. 支持每个用户拥有 6 个独立云存档槽位
5. 支持同一用户跨设备读取和保存自己的进度
6. 优先保证中国大陆用户在无 VPN 条件下能直接访问
7. 保留本地临时存档能力，避免网络波动时完全不可用

---

## 核心判断

### 一、第一版仍不建议自购云服务器

即使切换到 CloudBase 静态托管方案，第一版依然**不建议**直接购买并维护：

- 云服务器 CVM / ECS / VPS
- 自建 Node 服务
- 自建数据库
- 自建鉴权系统
- 自建邮件服务

原因不变：

1. 你的核心目标是“先把网页游戏账号系统做成并可用”，不是“学习完整后端运维”
2. 自建会显著增加：
   - 运维门槛
   - 安全风险
   - 备份责任
   - 证书、域名、数据库、邮件、审计复杂度
3. 本项目真正需要的后端能力并不复杂：
   - 认证
   - 每用户私有存档
   - 找回密码
   - 少量管理数据

因此，本项目第一版最合理的路线仍然是：

**前端静态托管 + CloudBase 认证 + CloudBase 数据库**

## 推荐方案

### 结论

本项目推荐采用：

1. **前端部署：CloudBase 静态网站托管**
2. **账号与云存档：CloudBase**
3. **访问方式：优先使用 CloudBase 默认域名进行测试与第一版发布**
4. **如未来要长期正式运营，再考虑自定义域名与备案**

不再推荐作为当前第一版主方案的方向：

- EdgeOne Pages 作为默认发布入口
- Cloudflare Pages + Supabase
- 海外静态托管 + 海外数据库认证
- 自购服务器 + 自建鉴权 / 自建数据库

## 为什么改成 CloudBase 静态托管

### 一、最符合“先不买域名、不做备案”的当前目标

CloudBase 静态网站托管官方明确提供：

- 默认域名
- 直接访问能力
- 适合开发和测试使用

这使得你当前可以先不处理：

- 域名购买
- DNS 配置
- ICP 备案

就把第一版账号与云存档功能跑起来。

### 二、前端、认证、数据库都在同一套产品里

改用 CloudBase 静态托管之后，整个第一版栈就统一成：

- 静态网站托管：CloudBase
- 身份认证：CloudBase
- 数据库：CloudBase

好处是：

1. 控制台更集中
2. 跨域和来源配置都在同一套环境里处理
3. 少一层第三方平台切换成本

### 三、未来仍可平滑升级

如果后续你准备：

- 长期正式公开运营
- 配自己的域名
- 做品牌化入口

CloudBase 静态托管同样支持自定义域名。只是官方也明确说明：

- 默认域名适合开发和测试
- 生产环境建议使用自定义域名
- 默认域名存在访问频率限制

所以这套方案是：

**先用默认域名做第一版，后续再决定是否升级为正式域名。**

## 总体架构

### 一、最终架构图

```text
玩家浏览器（手机 / PC）
    ↓
CloudBase 静态网站托管（默认域名）
    ↓
CloudBase Auth（账号、登录、会话）
    ↓
CloudBase Database（每用户云存档）
```

### 二、职责划分

#### 1. CloudBase 静态网站托管负责

- 托管前端网页
- 提供默认访问域名
- 提供 HTTPS
- 支持移动端浏览器直接访问

#### 2. CloudBase 认证负责

- 账号注册
- 登录会话
- 找回密码 / 邮箱验证链路

#### 3. CloudBase 数据库负责

- 每个用户的私有云存档
- 基于安全规则限制访问权限

#### 4. 前端负责

- 登录 / 注册 / 找回密码 UI
- 登录状态管理
- 保存到云端
- 从云端加载存档
- 网络失败时回退到本地缓存

## 静态托管方案

### 一、主方案：CloudBase 静态网站托管默认域名

第一版建议直接使用：

- CloudBase 静态网站托管
- 默认域名

这样可以：

1. 避开 EdgeOne 3 小时预览链接限制
2. 避开第一时间购买域名和备案
3. 让你先完成账号与云存档联调

### 二、CloudBase 默认域名的定位

默认域名适合：

- 开发
- 联调
- 测试
- 小范围试玩

不适合直接定义为最终长期正式版，因为官方说明默认域名存在访问频率限制。

### 三、后续升级路径

如果后面准备正式对外长期发布，再升级为：

1. CloudBase 自定义域名
2. 或迁移回其他正式静态托管入口

但这一步不应阻塞当前账号和云存档开发。

## 认证方案

### 一、第一版推荐：邮箱作为账号标识

虽然你提的是“用户名和密码”，但第一版依然建议：

- 底层登录标识：邮箱
- UI 可显示为“账号”

原因：

1. CloudBase 原生支持邮箱登录
2. 用户名密码登录路径并不是最简单的首版方案
3. 对当前项目而言，先把“邮箱 + 密码 + 云存档”做成，比一开始做真正的用户名体系更稳

### 二、找回密码

必须做。

只要做了密码登录，就必须提供：

- 忘记密码入口
- 邮件重置流程

## 存档策略

### 一、继续采用“双层存档”

不要把现有本地存档完全删掉。  
应改为：

1. **本地存档层**
   - 快速读写
   - 页面刷新恢复
   - 断网兜底

2. **云存档层**
   - 用户级持久存档
   - 跨设备同步
   - 正式账号系统下的主存档来源

### 二、第一版同步规则

采用最稳妥的规则：

**最后写入覆盖（last write wins）**

即：

- 每条存档以 `updatedAt` / `savedAt` 为准
- 保存时直接覆盖该用户该槽位旧记录
- 登录后拉取云端 6 个槽位
- 云端为空则显示空槽

第一版不要做复杂冲突合并。

## 数据库设计

### 一、主集合：`save_slots`

第一版建议使用：

- 集合名：`save_slots`

逻辑结构如下：

```ts
type CloudSaveSlot = {
  _id?: string;
  userId: string;
  slotId: number;
  version: number;
  chapterName: string;
  sceneName: string;
  inkStateJson: string;
  history: unknown[];
  dialogueHistory: unknown[];
  savedAt: string;
  createdAt: string;
  updatedAt: string;
};
```

### 二、业务约束

1. 每个用户固定 6 个槽位
2. 每个 `userId + slotId` 只保留 1 条当前有效记录
3. 保存策略为同槽位覆盖
